# Git 提交信息生成与推送

## 适用场景

- 用户要求为当前暂存的修改生成提交信息。
- 用户希望提交（commit）并推送（push）代码。
- 关键词：提交、commit、提交信息、commit message、推送、push。

## 工作流程

### 1. 读取暂存修改

先查看暂存区内容，不要直接使用未暂存的修改：

```bash
git status --short
git diff --cached --stat
git diff --cached
git log --oneline -10
```

- 只针对**已暂存（staged）**的改动生成提交信息。
- 参考最近提交历史，保持提交信息风格一致（本仓库使用中文提交信息）。
- 本仓库提交信息规范：中文、`类型: 简要描述` 形式（如 `docs: 更新 README`、`fix: 修复 xx`）。若暂存改动与某文件头部的 changelog 相关，可一并提示。

### 2. 生成多条提交信息样例

根据改动内容生成 **3~5 条**不同侧重点的中文提交信息，覆盖不同风格：

- 简洁型：短小精悍，只概括改动核心。
- 标准型：`类型: 描述`，符合 Conventional Commits / 本仓库习惯。
- 详细型：含简要正文，说明改了什么、为什么改。
- 类型型：一条按模块/文件拆分多条提交建议（`feat:`/`fix:`/`docs:`/`refactor:` 等）。
- 总结型：用一句话概括整个改动对用户的价值。

### 3. 询问用户确认

列出所有样例（编号 1~N），用 `question` 工具询问用户选择哪一条，并提供"自定义提交信息"选项（用户可输入自己的信息）。

### 4. 执行提交

用户确认后：

```bash
git commit -m "选中的提交信息"
```

- 如果用户选择的样例是多条提交建议，则按顺序执行多条 `git commit -m ...`。
- 提交失败（如 hook 拒绝）时，修复问题后新建提交，不要 amend 失败的提交。

### 5. 推送

提交成功后询问或直接推送：

```bash
git push
```

- 若存在上游分支则直接推送；若失败提示用户。
- 只有用户明确要求时才创建 PR；推送前不要修改 git config、跳过 hook。

## 注意事项

- 提交信息使用中文，与仓库既有提交风格一致。
- 不要在用户未确认前执行 `git commit` / `git push`。
- 只提交已暂存的内容，不自动 `git add` 其他文件；除非用户明确要求。
- 不要提交敏感信息（密钥、token 等）。
- 仓库 AGENTS.md 规定：任何代码修改前必须先出方案并获确认，但生成提交信息本身不修改代码文件。
